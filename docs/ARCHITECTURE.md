# 북작 (BOOKJAK) — 아키텍처

표준 FSD를 그대로 따르지 않는다. 아래 규칙을 우선한다.

---

## 레이어

`app / views / widgets / features / entities / shared`
표준 FSD에 없는 **`views` 레이어를 추가**로 둔다.

- **`app/`** — 라우팅 껍데기만. 실제 로직을 두지 않는다. 페이지 컴포넌트는 `views/*/ui/*View.tsx`를 **렌더링만 위임**한다.
  *(이유: 라우팅과 화면 로직을 섞으면 라우트 변경이 화면 코드를 흔든다.)*

- **`views/`** — 폴더명은 라우트 경로를 kebab-case로 평탄화한 것.
  예: `social/clubs/[id]` → `views/social-club-detail`, `social` 루트 → `views/social-hub`.
  새 라우트를 만들 때 이 매핑 규칙을 지킨다.

---

## entities 규칙

- **`ui/model/api` 3종을 항상 다 만들지 않는다.** 실제로 필요한 서브폴더만 만든다.
  예: `book`은 `model/`만, `user`는 `model/` + `api/` + `ui/`.
  *(이유: "entity니까 3종 세트"는 이 프로젝트 규칙이 아니다. 안 쓰는 빈 폴더는 노이즈다.)*

---

## features 규칙

- **폴더명은 명사형으로.** 동사형이 아니라 명사형.
  예: `nickname-gate`, `follow`, `like`, `wishlist`.

---

## "어디에 둘 것인가" — 공통 배치 기준

> 새로 만들 때 반사적으로 공통(`shared`)에 넣지 않는다.

무엇을 `shared`에 두고 무엇을 화면 쪽에 둘지, **아래 기준으로 판단**한다.

- **`shared`에 둔다** — 도메인 지식이 전혀 없는 최하단 요소. "이게 북작인지 몰라도 다른 앱에 그대로 옮길 수 있는가?"가 참일 때. (예: `Button`, `Input`)
- **화면(view/feature)에 둔다** — 특정 화면·기능에서만 쓰는 것. 지금 한 곳에서만 쓰면 일단 그 화면에 둔다.
- **판단 기준: "지금 두 곳 이상에서 실제로 쓰이는가?"**
  아니면 화면에 둔다. 나중에 두 번째 사용처가 생기면 그때 `shared`로 올린다.
  *(이유: 미리 공통화하면, 한 곳만 바뀌어야 할 때 다른 곳까지 깨진다. 잘못된 공통화는 중복보다 비싸다.)*

---

## 리팩토링 · 삭제 규칙

- 기능을 지우거나 리팩토링할 때는 **관련된 것을 전부** 찾아 지운다.
  컴포넌트, `model`, `api`, 타입, import 참조, 안 쓰게 된 라우트/뷰 폴더까지.
- **흔적을 남기지 않는다** — 죽은 export, orphan 파일, 주석 처리된 코드.
